# ADR 0008: Chat decisions

- Status: Accepted
- Date: 2026-11-20
- Source: code comments removed in the comment cleanup

## Chat book selector visibility and locked own book

**Context.** The chat can include multiple open books; the chat's own book must always be included, and a selector is useless with fewer than two open books (including the standalone reader, which has no open books).

**Decision.** ChatBookSelectorMenu renders one circular checkbox row per open book, locks ownBookId as checked, and returns null when fewer than two books are open.

**Consequences.** The selector only appears in multi-book workspaces.

**Code.** `app/components/chat/chat-book-selector.tsx#ChatBookSelectorMenu`

## Book selector menu stays open on toggle

**Context.** Users often include several books at once.

**Decision.** CircularCheckboxItem sets closeOnClick={false} so the menu stays open across toggles.

**Consequences.** Users close the menu explicitly.

**Code.** `app/components/chat/chat-book-selector.tsx#CircularCheckboxItem`

## Book selector uses raw Base UI CheckboxItem for circular indicator

**Context.** The exported shadcn DropdownMenuCheckboxItem renders a square check indicator; the book selector spec requires a round one.

**Decision.** CircularCheckboxItem wraps MenuPrimitive.CheckboxItem directly with a circular indicator.

**Consequences.** Separate styling from the shared checkbox item must be kept in sync manually.

**Code.** `app/components/chat/chat-book-selector.tsx#CircularCheckboxItem`

## Static cross-book starter prompts

**Context.** Empty-state suggestions for 2+ selected books could be generated, but that costs an LLM call.

**Decision.** crossBookCategory returns static prompts with book titles interpolated where natural.

**Consequences.** Suggestions are free and instant but generic.

**Code.** `app/components/chat/chat-empty-state.tsx#crossBookCategory`

## Gated chat input opens onboarding once passively

**Context.** When chat is gated (needs onboarding), repeatedly opening the dialog on every focus would block typing.

**Decision.** passiveOpenGuardRef opens the onboarding dialog only on the first focus/click; later focus and typing pass through; submit always re-opens the dialog with the current text.

**Consequences.** Users see the CTA once and can still draft a message.

**Code.** `app/components/chat/chat-input.tsx#passiveOpenGuardRef`

## Memoize ChatMessage for streaming performance

**Context.** The chat panel re-renders on every streamed token; without memoization every historical message re-runs text joins and re-renders its Streamdown markdown tree per token.

**Decision.** ChatMessage is wrapped in React.memo. useChat keeps stable references for unchanged messages (only the streaming message is replaced), so a shallow prop compare skips settled messages.

**Consequences.** Relies on useChat preserving message identity; passing new object/callback props per render would defeat it.

**Code.** `app/components/chat/chat-message.tsx#ChatMessage`

## resolveBookTitle falls back to the chat primary book

**Context.** Older search_book tool outputs have no bookId field; new outputs may also reference unknown ids.

**Decision.** resolveBookTitle uses the chat's own bookId when the tool output id is absent, then looks it up in the workspace books list.

**Consequences.** Old persisted chats still show book labels on search results.

**Code.** `app/components/chat/chat-message.tsx#resolveBookTitle`

## Chat transport sends only the latest message plus routing context

**Context.** The server loads prior chat history from Postgres, so shipping the full message list is wasteful; multi-book selection can change between renders; streams can be resumed; and a brand-new book/session may not yet be synced when chat is first used.

**Decision.** createChatTransport POSTs only the latest user message with sessionId, bookId, visibleText and currentChapterIndex (kept for back-compat) plus the additive multi-book contract bookIds (primary first, deduped, demo book removed) and a per-book bookContexts map. selectedBookIdsRef is read at send time, not from a closure. reconnectToStream goes to /api/chat/resume/:sessionId, which replays an in-flight Redis stream. Only POST /api/chat is retried (resume/messages endpoints have their own ownership checks and must not race on creation): on a 404 for book/session or a specific 400 for missing chapters it retries with delays CHAT_SEND_RETRY_DELAYS_MS (250/500/1000ms), each time requesting a sync push and awaiting chapter upload, and reports a preparing state.

**Consequences.** Server must accept both legacy single-book and multi-book fields.

**Code.** `app/components/chat/chat-utils.ts#createChatTransport`

## Normalize AI SDK static and dynamic tool parts

**Context.** AI SDK UI messages encode static tool parts as type "tool-{toolName}" and dynamic tools as type "dynamic-tool" with a toolName field.

**Decision.** getToolInfo normalizes both to { toolName, state, input, output } and returns null for non-tool parts.

**Consequences.** All chat code reads tool parts through getToolInfo.

**Code.** `app/components/chat/chat-utils.ts#getToolInfo`

## Restore spaces when joining assistant text parts

**Context.** Assistant responses are split into multiple text parts at step/tool boundaries. A naive join("") drops whitespace the model emitted right at a boundary, producing "...end of chunk.Next sentence".

**Decision.** joinTextParts inserts a single space only when the previous part ends with a non-whitespace character and the next begins with one, so sentence/paragraph boundaries keep a separator while mid-word splits and markdown (code fences, lists) are not corrupted.

**Consequences.** A mid-word split between two non-whitespace characters will gain a space.

**Code.** `app/components/chat/chat-utils.ts#joinTextParts`

## Chat messages: server is source of truth, IDB is a warm-start cache

**Context.** Chats must render instantly on cold reload but the server owns history.

**Decision.** uiMessagesToChatMessages converts useChat messages for the local IDB warm-start cache, used only when reconciling server history into IDB. It filters out ephemeral client-only book add/remove markers (ids prefixed "annot-") defensively, even though they live in a separate render-only list.

**Consequences.** IDB never holds client-only annotations.

**Code.** `app/components/chat/chat-utils.ts#uiMessagesToChatMessages`

## Apply server-run append_to_notes results on the client in onFinish

**Context.** append_to_notes runs on the server, which parses markdown, persists the notebook to Postgres and returns the appended TipTap nodes plus full updatedContent and server updatedAt. The client may already have shown a streaming preview.

**Decision.** For each output-available append_to_notes part, onFinish: always consumes the toolCallId entry from streamedToolCallIdRef (even when nothing was appended) so the map does not grow across messages; routes to output.bookId or the primary bookId; if output.appended is false, restores the authoritative server snapshot when available or rolls back to the pre-preview content; otherwise appends the nodes to the live editor only when no streaming preview already inserted them (to avoid duplicates); and, independently of whether the editor is open, seeds the editor lastContentRef and writes the snapshot to IndexedDB via cacheNotebook, then dispatches sync:entity-updated {notebook} so useSyncListener consumers (book details, notebook preview) see the notes without waiting for a sync pull. Seeding lastContentRef first makes the workspace-notebook listener treat the event as a no-op, avoiding a setContent that would reset the cursor.

**Consequences.** Correctness depends on useStreamingAppend recording previews in the shared map.

**Code.** `app/components/chat/use-chat-tool-handlers.ts#onFinish`

## create_highlight resolves the target book data and format per call

**Context.** In multi-book chat a highlight can target a book other than the open primary reader, whose bytes are not loaded. The server signals PDFs with unsupported: "pdf" because it only executes the epub path.

**Decision.** For the primary book the handler reuses bookDataRef/bookFormat; for other books it loads the ArrayBuffer with BookService.getBookData. Format is "pdf" when output.unsupported === "pdf", else the primary format for the primary book, otherwise treated as epub. If the server created the highlight (epub only) its row and text anchor are used: the CFI is taken from the server or resolved by fuzzy search, preferring the server text-anchor snippet (the server already found the best chapter) and falling back to the full text. PDFs use client-side text search to find a page. AI-created highlights never navigate the reader, to preserve reading position; they are appended to the notebook (live editor callback or saga fallback).

**Consequences.** Non-primary PDFs are only detected via the server unsupported signal.

**Code.** `app/components/chat/use-chat-tool-handlers.ts#onFinish`

## Route chat tool outputs by echoed bookId, falling back to the primary book

**Context.** Multi-book chat lets tools act on any selected book; older tool outputs (and edit_notes, which today runs against the primary notebook) may not echo a bookId.

**Decision.** append_to_notes, edit_notes and create_highlight handlers use output.bookId when present and fall back to the chat's bound primary bookId for back-compat.

**Consequences.** Old persisted outputs still route correctly.

**Code.** `app/components/chat/use-chat-tool-handlers.ts#onFinish`

## Restore draft and allow retry when resumed chat message fails

**Context.** A message typed before signup is resumed after onboarding; if sending fails the user would lose the text and the de-dupe guard would block retry.

**Decision.** On failure useResumeMessage clears resumedMessageRef and writes the message back into inputRef and the textarea.

**Consequences.** Users can retry without retyping.

**Code.** `app/components/chat/use-resume-message.ts#useResumeMessage`

## Stream append_to_notes previews into the notebook editor

**Context.** The append_to_notes tool input streams token by token; users should see notes appear live, and onFinish must not append the same content twice or leave a preview behind if persistence fails.

**Decision.** useStreamingAppend watches the last assistant message for append_to_notes parts in input-streaming state, records the editor top-level node count and original content as a baseline, and replaces everything after the baseline with parsed partial markdown on each text change (replaceContentFrom). On input-available/output-available it does a final replace and records toolCallId -> pre-preview content in the shared streamedToolCallIdRef so onFinish can skip a duplicate append or roll back the preview.

**Consequences.** Preview and persistence are coupled through the shared ref.

**Code.** `app/components/chat/use-streaming-append.ts#useStreamingAppend`

## Chapter question cache is best-effort

**Context.** The IndexedDB cache for generated chapter questions can fail to read or write.

**Decision.** A failed cache read still makes the network request; a failed cache write still returns the generated questions.

**Consequences.** Caching never blocks chapter questions.

**Code.** `app/lib/chat/chapter-questions.ts#loadChapterQuestions`

## Chapter upload treats 401 and 503 as expected

**Context.** 401 means the user is signed out and 503 means sync is off; neither is a bug.

**Decision.** On 401 or 503, do not log an error and do not mark the book as uploaded, so the upload is retried on the next open.

**Consequences.** Quiet logs for signed-out users; uploads catch up once the user signs in or sync turns on.

**Code.** `app/lib/chat/upload-chapters.ts#uploadChapters`

## Chat markdown export includes only visible conversation text

**Context.** Chat messages contain visible text plus internal reasoning parts and tool call payloads.

**Decision.** chatToMarkdown exports only the visible conversation text and excludes reasoning and tool payloads.

**Consequences.** Exports are readable transcripts, not full message dumps; reasoning/tool data are not recoverable from an export.

**Code.** `app/lib/export/chat-markdown.ts#chatToMarkdown`

## Orama book index cache holds a single entry

**Context.** Building an Orama index for a whole book is costly, but indexes are large.

**Decision.** Use an LRU-1 cache (cachedKey/cachedIndex) storing only the most recent book index.

**Consequences.** Bounded memory; switching between books rebuilds the index.

**Code.** `app/lib/orama-book-search.ts#getOrBuildBookIndex`

## Verify Orama hits with normalized substring search before fuzzy fallback

**Context.** locateTextAnchor maps a passage to chapter + snippet + offset for client-side CFI resolution; Orama results alone can be fuzzy.

**Decision.** Use the Orama result as the first candidate, then verify normalized substrings across every chapter, and only accept a fuzzy fallback if no exact match exists.

**Consequences.** More accurate anchors at the cost of scanning all chapters.

**Code.** `app/lib/orama-book-search.ts#locateTextAnchor`

## Normalize quotes, dashes and whitespace before matching AI quotes

**Context.** AI-generated quotes of book text often differ from the source in quote styles, dashes and whitespace.

**Decision.** normalizeForMatch folds curly quotes, dash variants and whitespace before substring matching.

**Consequences.** Quotes resolve to anchors despite typographic differences; offsets must be computed against normalized text carefully.

**Code.** `app/lib/orama-book-search.ts#normalizeForMatch`

## Treat Orama v3 search() as synchronous

**Context.** Orama v3 search() is typed to return a value or a promise.

**Decision.** Because the schema has no async components, the result is cast with Awaited<typeof raw> and used synchronously.

**Consequences.** Adding async components (e.g. embeddings plugins) would break this assumption.

**Code.** `app/lib/orama-book-search.ts#searchBook`

## Bullet rating threshold tolerates floating-point roundoff

**Context.** Normalized ratings are floats and can land just below an inclusive threshold due to roundoff.

**Decision.** Accept when rating >= threshold - Number.EPSILON.

**Consequences.** Only roundoff is tolerated; the boundary remains inclusive.

**Code.** `app/lib/reading-agent/jev.server.ts`

## Capture Jev provider usage before SDK answer validation

**Context.** The SDK validates evaluation answers (and may observe cancellation) after the provider call has already consumed tokens.

**Decision.** Wrap model.doEvaluate to record response.usage before the SDK validates or cancels.

**Consequences.** Token usage is accounted even when validation fails or the call is cancelled.

**Code.** `app/lib/reading-agent/jev.server.ts`

## Normalize Jev bullet scores by dividing by 2

**Context.** Jev scores interpolate zero-based rubric indices; the bullet rubric has three rungs (0,1,2).

**Decision.** Divide answer.score by 2 to normalize to [0,1].

**Consequences.** Changing the rubric length requires changing the divisor.

**Code.** `app/lib/reading-agent/jev.server.ts`

## Adjacent page context is truncated toward the current page

**Context.** Previous/next page text sent as context is bounded by MAX_ADJACENT_PAGE_TEXT_LENGTH.

**Decision.** boundAdjacentPageText keeps the end of the previous page and the start of the next page, i.e. the portion closest to the current page.

**Consequences.** Most relevant context is retained when pages are long.

**Code.** `app/lib/reading-agent/page-context.ts#boundAdjacentPageText`

## Reject oversized review inputs rather than clipping

**Context.** Review prompts include the full chapter and answer; clipping would grade against partial text.

**Decision.** Use conservative UTF-8 budgets (REVIEW_MAX_CHAPTER_BYTES 80k, REVIEW_MAX_PROMPT_BYTES 160k) and reject oversized inputs.

**Consequences.** Very long chapters cannot be reviewed, but grades are never based on truncated text.

**Code.** `app/lib/review/review-model.server.ts`

## Repair model annotation offsets only for exact unique quotes

**Context.** Models quote the answer correctly but miscount UTF-16 offsets.

**Decision.** When start/end do not match the quote, relocate only if the quote appears exactly once; otherwise drop the optional annotation, never the grade.

**Consequences.** Annotations are accurate or absent; grades are not discarded for bad annotations.

**Code.** `app/lib/review/review-model.server.ts`

## AI highlights carry a text anchor until the client resolves a CFI

**Context.** When the AI calls create_highlight on the server, no CFI is known (CFIs require the rendered epub).

**Decision.** The server stores a HighlightTextAnchor (chapterIndex, snippet, optional offset); the client resolves it to a CFI inside the epub iframe and updates the highlight via LWW sync.

**Consequences.** Highlights exist before a CFI is known; clients must resolve and write back anchors.

**Code.** `app/lib/stores/annotations-store.ts#HighlightTextAnchor`

## Appending a chat message never advances session updatedAt

**Context.** Session updatedAt is the LWW clock for session-row metadata (title, bookId, deletedAt).

**Decision.** mergeChatMessageRecord only grows session.messages and never changes session.updatedAt.

**Consequences.** Bumping the clock would make later server-side title or tombstone merges lose LWW against a stale local row.

**Code.** `app/lib/sync/entity-mergers.ts#mergeChatMessageRecord`

## Pulled chat messages are appended in server order, not sorted

**Context.** Sorting cached messages by createdAt was unreliable because some messages had createdAt of 0.

**Decision.** mergeChatMessageRecord is append-only by message id; it relies on the server returning messages in created_at ASC order and pushes new messages without sorting.

**Consequences.** Message order depends on server delivery order; out-of-order delivery would persist out of order.

**Code.** `app/lib/sync/entity-mergers.ts#mergeChatMessageRecord`

## Chat session merge is metadata-only LWW and keeps local messages

**Context.** Server session rows carry only metadata; messages sync separately as chat_message records but are cached inside the local session value.

**Decision.** When the remote session is strictly newer, replace session metadata with the remote copy but keep local messages; new sessions from the server are added with an empty messages array.

**Consequences.** Session metadata and messages have independent merge rules.

**Code.** `app/lib/sync/entity-mergers.ts#mergeChatSessionRecord`

## Chat session tombstones remove the local session and its cached messages

**Context.** Chat sessions are stored per bookId as a ChatSession[] in IDB, and cached messages live inside the same array value. Session metadata merges with LWW on updatedAt.

**Decision.** When a pulled session has deletedAt, mergeChatSessionRecord removes it locally (removeSessionLocally) unless the local updatedAt is strictly newer than the tombstone. Equal timestamps lose, matching the other LWW mergers, so a session re-created locally in the same millisecond is removed. Losing the cached messages is acceptable because the server is the source of truth if the session is un-deleted.

**Consequences.** Deletes propagate across devices; a same-millisecond local re-create loses.

**Code.** `app/lib/sync/entity-mergers.ts#mergeChatSessionRecord`

## Chat messages are server-authoritative and never pushed from clients

**Context.** Chat sessions are stored locally with their messages, but /api/chat persists messages on the server as they are generated.

**Decision.** Client sync records only chat session metadata; the messages array is stripped before recordChange (initial backfill included).

**Consequences.** Avoids clients overwriting or duplicating server-side message history; message content only flows server to client.

**Code.** `app/lib/sync/initial-sync.ts#runInitialSyncIfNeeded`

## Client uploads extracted chapter text to a server cache

**Context.** Chat runs server-side and needs book text, but EPUB/PDF parsing is client-only.

**Decision.** The client POSTs extracted chapters once per book on first open (legacy single body or chunked {uploadId, chunkIndex, totalChunks, totalChapters}); server upserts per (userId, bookId) and verifies ownership.

**Consequences.** Chat requires a prior chapter upload; chunked uploads use an upload-session lock.

**Code.** `app/routes/api.books.$bookId.chapters.ts#action`

## Resume endpoint self-heals stale active_stream_id

**Context.** resumeExistingStream returns a stream (in flight), null (finished) or undefined (missing: function died before onFinish cleared the id, or Redis key expired). Passing nullish into Response left clients hanging on an empty 200 SSE and the session pointing at a dead stream forever.

**Decision.** No active id -> 204 (AI SDK DefaultChatTransport with resume:true treats empty 204 as idle). null/undefined -> clear active_stream_id and return 204. Thrown errors are treated as transient Redis/network failures -> 503 and keep the id.

**Consequences.** Clients may retry on 503; stale ids are cleared so later resumes short-circuit.

**Code.** `app/routes/api.chat.resume.$sessionId.ts#loader`

## Bounded multi-step tool use with forced final synthesis

**Context.** Reading-companion answers may need several tool rounds (book search/read, web search, recommendations, highlights, notes).

**Decision.** Cap at MAX_CHAT_STEPS (20); on the last step prepareStep sets activeTools to [] so the model must produce text.

**Consequences.** Answers never end on a dangling tool call.

**Code.** `app/routes/api.chat.ts#action`

## Multi-book chat selection: strict primary, lenient secondaries

**Context.** Chat can include several books. Older clients send a single bookId plus top-level visibleText/currentChapterIndex.

**Decision.** bookIds[0] is primary (fallback legacy bookId); list de-duplicated with primary first; top-level bookId not required when bookIds present. Primary must have chapters (else error). Legacy top-level context applies to primary when bookContexts lacks it. Secondaries that are missing, lack chapters or have stale chapter shape are skipped with a warning. Tools take optional bookId; unknown/omitted ids fall back to primary so model mistakes never fail a tool; the tool description lists valid ids when multiple books are loaded.

**Consequences.** Requests degrade gracefully; the system prompt receives books primary-first plus warnings.

**Code.** `app/routes/api.chat.ts#action`

## Persist the user message before streaming

**Context.** A crashed stream would otherwise lose the user turn.

**Decision.** upsertMessage the incoming user message before starting streamText.

**Consequences.** History contains the user turn even when generation fails.

**Code.** `app/routes/api.chat.ts#action`

## Verify chat session ownership before reading or writing

**Context.** sessionId comes from the client.

**Decision.** Look up the session with getSessionByIdForUser and 404 if not owned before loading history or persisting messages.

**Consequences.** Prevents cross-user leakage or injection into another user's chat session.

**Code.** `app/routes/api.chat.ts#action`

## Retry post-stream chat persistence with linear backoff

**Context.** Postgres is the source of truth for chat history; the assistant message is written once after streaming, and active_stream_id is recorded after the resumable stream is created.

**Decision.** Wrap these writes in withRetries (default 3 attempts, 250ms linear backoff; attempts clamped to >=1 so lastError is never undefined). Record active_stream_id only after stream creation so resume never races a not-yet-created Redis stream; if resumable stream creation fails, skip recording and serve the direct stream.

**Consequences.** Transient DB failures no longer make messages vanish on reload or streams silently unresumable.

**Code.** `app/routes/api.chat.ts#withRetries`
