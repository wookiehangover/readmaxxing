# ADR 0001: Sync decisions

- Status: Accepted
- Date: 2026-11-20
- Source: code comments removed in the comment cleanup

## Cache server-persisted notebook snapshots without recording a local change

**Context.** After a server-run notebook tool the server already holds the new state. saveNotebook would recordChange and echo the same value back to the server on the next sync push.

**Decision.** Chat tool handlers write server snapshots with cacheNotebook (cacheNotebookRequested) using the server updatedAt, not saveNotebook.

**Consequences.** No redundant sync pushes; local cache matches server truth.

**Code.** `app/components/chat/use-chat-tool-handlers.ts#cacheNotebookSnapshot`

## Sync error indicator is sticky for 3s

**Context.** Consecutive failed sync cycles toggle error -> syncing -> error, which flickers.

**Decision.** useStickyError shows new errors immediately and keeps a cleared error visible until at least minMs (3000ms) has passed since it appeared. SyncStatus uses this sticky error in its offline > error > syncing > pending > synced priority.

**Consequences.** Errors are noticeable; the error may display up to 3s after recovery.

**Code.** `app/components/sync-status.tsx#useStickyError`

## PDF reader flushes its debounced position save on pagehide

**Context.** Position saves are debounced. A page turn inside the debounce window would be lost on refresh or close, and the older server position would then win last-write-wins on the next pull.

**Decision.** Listen for window pagehide and call flushPositionSave.

**Consequences.** The last page survives refresh/close; the same pattern is needed for any debounced reader save.

**Code.** `app/hooks/use-pdf-lifecycle.ts#flushPositionSave`

## Dedup cross-device book uploads by file hash with tombstoned losers

**Context.** The same EPUB can be uploaded from several devices, producing distinct book ids with the same file_hash.

**Decision.** On push, findBookByUserAndHash picks the canonical book as the earliest-created non-deleted row for user+file_hash, breaking created_at ties (e.g. bulk backfill with identical timestamps) by id ASC so every replica selects the same winner. The losing id is written as a tombstone via insertTombstonedBook so the soft-delete propagates to other devices through pull: an existing non-deleted row is soft-deleted in place, an already-deleted row is a no-op, and the operation is idempotent.

**Consequences.** Canonical selection is deterministic across replicas; losing ids appear to other devices as deletions.

**Code.** `app/lib/database/book/book.ts#findBookByUserAndHash`

## Clamp client-provided timestamps on sync writes

**Context.** Sync pulls use updated_at/deleted_at cursors. A device with a fast or adversarial clock could write far-future updated_at, created_at or deleted_at values; a future deleted_at would match `deleted_at > cursor` on every pull forever and be re-delivered to every device each sync cycle.

**Decision.** All client-provided timestamps are clamped to at most DEFAULT_UPDATED_AT_SKEW_MS (5 minutes) after server NOW() before being bound into SQL. clampUpdatedAt falls back to server NOW() for null/undefined/invalid input. clampNullableTimestamp preserves null/undefined as SQL NULL (for nullable columns like deleted_at) but maps an invalid Date to server NOW(), because for a tombstone the intent to delete is clear even if the clock value is garbage. Highlight and bookmark upserts clamp created_at and deleted_at as well as updated_at.

**Consequences.** Client clock skew beyond 5 minutes is silently corrected server-side; every new sync write path must apply the same clamp to every client timestamp column.

**Code.** `app/lib/database/clamp-timestamp.ts#clampUpdatedAt`

## Demo content is re-keyed with account-specific ids before first push

**Context.** Demo book and chat ids are fixed constants, but database primary keys are global across all accounts.

**Decision.** persistAdoptedDemoContent assigns a new random book id (and session ids) to adopted demo content before the first server push.

**Consequences.** Multiple accounts can adopt the demo without primary-key collisions; demo ids never reach the server.

**Code.** `app/lib/onboarding/adopt-demo.ts#persistAdoptedDemoContent`

## Demo seeding writes IDB directly without recording sync changes

**Context.** Demo content is seeded for signed-out visitors, who have no account to sync to.

**Decision.** seed writes chat sessions directly with idb-keyval set() instead of the sync-aware store APIs, so no sync change is recorded.

**Consequences.** Seeded demo data never pushes to the server; adoption on sign-in must explicitly record changes.

**Code.** `app/lib/onboarding/demo-seed.ts`

## Panel position saves do not record a sync change

**Context.** In workspace mode a page turn saves the position under both the panelId and the bookId. Recording both produced two sync changelog entries per page turn.

**Decision.** The panel-keyed save passes recordChange:false; only the bookId save records a change.

**Consequences.** One changelog entry per page turn; the panel position stays local-only.

**Code.** `app/lib/position-utils.ts#savePosition`

## Only the book-level reading position save records a sync change

**Context.** Positions are saved under a panel key and a book key. Panel ids are random per-session UUIDs that no other device queries.

**Decision.** savePositionDualKey writes the panel key as a device-local mirror (never recorded for sync); only the book-level save records a sync change, and recordChange: false makes both writes local-only. When panelId is undefined only the book key is written.

**Consequences.** Halves page-turn sync traffic; other devices only see book-level positions.

**Code.** `app/lib/position-utils.ts#savePositionDualKey`

## Review drafts are local-only and account-scoped

**Context.** Drafts hold unsubmitted answers.

**Decision.** ReviewDraft is stored locally per account and must never be pushed as a graded attempt or shared question.

**Consequences.** Drafts do not sync across devices.

**Code.** `app/lib/review/review-types.ts#ReviewDraft`

## Legacy settings migration drops the synced updatedAt

**Context.** UI fields used to live in the synced app-settings blob; a font change bumped updatedAt under the old schema.

**Decision.** migrateLegacySettings moves UI fields into the local-only bucket (existing local values win, legacy copies are pruned, idempotent) and deletes updatedAt from the synced bucket so a legacy timestamp cannot make LWW ignore newer remote theme/colorTheme updates; the next remote pull establishes a fresh baseline.

**Consequences.** Migrated clients accept remote synced settings after migration.

**Code.** `app/lib/settings.ts#migrateLegacySettings`

## Settings migration drops the legacy updatedAt timestamp

**Context.** Before UI fields moved to a local bucket, any local change such as fontSize bumped the synced settings updatedAt, which then blocked newer remote settings in last-write-wins merges.

**Decision.** The migration that splits synced and local settings removes updatedAt from the synced bucket.

**Consequences.** Remote synced settings apply after migration even if their timestamps are older.

**Code.** `app/lib/settings.ts#migrateLegacySettings`

## Split settings into synced (LWW) and local-only buckets

**Context.** Some settings (theme, colorTheme) should follow the user across devices, while layout and typography are per-device.

**Decision.** SyncedSettingsSchema fields sync via the 'settings' entity with last-write-wins on updatedAt; LocalUISettingsSchema fields stay in a separate local-only localStorage bucket and never sync. SettingsSchema merges both as the backward-compatible shape exposed to call sites.

**Consequences.** Call sites see one settings object; storage and sync treat the two buckets separately.

**Code.** `app/lib/settings.ts#SyncedSettingsSchema`

## cacheNotebook seeds IDB without recording a sync change

**Context.** When the server is authoritative (e.g. edit_notes tool output), recording a change would make the sync engine echo the same value back on the next push.

**Decision.** cacheNotebook writes the notebook to IndexedDB for warm start without adding a change log entry.

**Consequences.** Local cache matches server state without redundant pushes.

**Code.** `app/lib/stores/annotations-store.ts#cacheNotebook`

## Deduplicate synced book files by SHA-256

**Context.** The same book file can be uploaded from multiple devices.

**Decision.** BookMeta.fileHash stores the SHA-256 of the file data and is used to deduplicate during sync upload.

**Consequences.** Identical files share a remote blob.

**Code.** `app/lib/stores/book-store.ts#BookMeta`

## Soft-delete tombstones for synced entities

**Context.** Deletes must propagate to other devices through LWW sync; removing the record locally would leave nothing to push.

**Decision.** Deleting a book or highlight sets deletedAt (and updatedAt) and keeps the record as a tombstone; readers treat records with deletedAt as deleted.

**Consequences.** Tombstones accumulate in IDB; soft-deleted books can still be inspected and restored via getBookIncludingDeleted.

**Code.** `app/lib/stores/book-store.ts#deleteBook`

## chat_session sync is metadata-only LWW

**Context.** Chat messages are stored server-side separately; syncing them in session payloads would be large and conflict-prone.

**Decision.** The tracked chat_session change payload excludes messages; only session metadata (bookId, title, timestamps) is synced via LWW.

**Consequences.** Messages are hydrated from the server separately.

**Code.** `app/lib/stores/chat-store.ts`

## Chat message hydration does not bump the session LWW clock

**Context.** chat_session sync is last-write-wins on updatedAt. Previously cacheServerMessages bumped updatedAt on every message hydration, so a rename from another device would lose LWW on the next pull.

**Decision.** cacheServerMessages writes messages without changing updatedAt and without enqueuing a sync change.

**Consequences.** Metadata edits from other devices (e.g. renames) are preserved.

**Code.** `app/lib/stores/chat-store.ts#cacheServerMessages`

## Migrate legacy chat messages into a default session

**Context.** Older clients stored a flat message array per book (ebook-reader-chats/chats) instead of sessions.

**Decision.** When getSessionsByBook finds no sessions but legacy messages exist, migrateOldMessages creates a default session from them, sets it active, and enqueues a sync change immediately instead of waiting for runInitialSyncIfNeeded to scan everything.

**Consequences.** Legacy chats appear as a session and reach the server promptly.

**Code.** `app/lib/stores/chat-store.ts#migrateOldMessages`

## Pulled chat session tombstones are applied without enqueuing a change

**Context.** The sync pull merger reconciles server-side tombstones the server already knows about.

**Decision.** removeSessionLocally removes the session (and its cached messages inside the per-book session array) from IDB and clears the active-session pointer if needed, without enqueuing a sync change.

**Consequences.** No delete echo on the next push.

**Code.** `app/lib/stores/chat-store.ts#removeSessionLocally`

## Keep the position LWW clock when only layout metadata changes

**Context.** Reopening a book triggers a relocation during restore that re-saves the same CFI, possibly with new layout metadata (localProgression, spineIndex).

**Decision.** When the saved CFI equals the stored CFI, savePosition keeps the existing updatedAt and only updates layout metadata, so reopening a book cannot make this device look newer than another device in LWW position merges.

**Consequences.** Same-CFI saves never bump updatedAt; a pending local-only change for that CFI is flushed to the changelog with the preserved timestamp.

**Code.** `app/lib/stores/position-store.ts#makePositionService`

## Saving an unchanged reading position is a no-op

**Context.** A stuck relocated-event source can repeatedly save the same CFI; bumping updatedAt and recording a change each time drives a 1 Hz sync-push loop.

**Decision.** savePosition skips the IDB write and recordChange when the CFI equals the stored one, leaving updatedAt unchanged.

**Consequences.** No sync churn from repeated identical relocations.

**Code.** `app/lib/stores/position-store.ts#savePosition`

## Panel-specific position mirrors are local-only writes

**Context.** savePositionDualKey writes a book position and a panel-specific mirror. Panel ids are device-local UUIDs that no other device can consume.

**Decision.** savePosition accepts recordChange (default true); the panel mirror passes recordChange: false so it is not appended to the sync changelog.

**Consequences.** Halves position pushes per page turn. Local-only writes are tracked in pendingLocalOnlyChanges and are enqueued later if a syncing save hits the same CFI.

**Code.** `app/lib/stores/position-store.ts#SavePositionOptions`

## One-time backfill re-pushes books with blob URLs

**Context.** Blob URLs used to reach Postgres only through the onUploadCompleted webhook in api.sync.files.upload.ts, which was unreliable (timing, silent failures, row-not-yet-inserted races). Books uploaded before push started carrying URLs have null cover_blob_url/file_blob_url in prod.

**Decision.** runBlobUrlBackfillIfNeeded re-enqueues a book change for every non-deleted local book with remoteFileUrl or remoteCoverUrl, so the push handler (updateBookBlobUrls with COALESCE) fills the columns. Gated by localStorage flag readmax:blob-url-backfill:v1 so it runs once per device; per-book errors are logged and skipped.

**Consequences.** Push, not the upload webhook, is the reliable path for blob URLs. A device that never runs the new code never heals its rows.

**Code.** `app/lib/sync/backfill-blob-urls.ts#runBlobUrlBackfillIfNeeded`

## One-time backfill of book fileHash

**Context.** Server-side dedup of books relies on fileHash, but books imported before hashing existed have no hash, so duplicate rows never converge.

**Decision.** runFileHashBackfillIfNeeded hashes every local book file lacking fileHash, writes it to meta with a fresh updatedAt, and enqueues a book change. Gated by localStorage flag readmax:file-hash-backfill:v1 so it runs once per device; per-book errors are logged and skipped.

**Consequences.** Pre-existing duplicates converge after each device pushes its hashes. Books whose bytes are not stored locally stay unhashed.

**Code.** `app/lib/sync/backfill-file-hash.ts#runFileHashBackfillIfNeeded`

## Change recording signals push: microtask for most entities, debounced for positions

**Context.** recordChange must tell the sync engine to push instead of waiting for the next interval. Dispatching synchronously can trigger React state updates during render, and position changes fire on every page turn.

**Decision.** Non-position changes dispatch sync:push-needed in a queueMicrotask. Position changes debounce the dispatch with a 5000 ms timer, so they sync soon for cross-device use without push-triggered re-renders during active navigation.

**Consequences.** Positions reach the server up to ~5s late; rapid page turns collapse into one push signal.

**Code.** `app/lib/sync/change-log.ts#recordChange`

## Dedup books by fileHash on pull by remapping local ids

**Context.** The same book file imported on two devices gets two ids. Without pull-side handling, the UI shows a duplicate until a later push/pull round converges.

**Decision.** mergeBookRecord, for a non-deleted incoming book with fileHash, finds a non-deleted local book with the same hash under a different id, calls remapBookId(localId, incomingId) to move all local references to the incoming canonical id, and dispatches sync:entity-updated for book, position, highlight, bookmark, notebook and chat_session. Only the first match is remapped.

**Consequences.** The server id wins as canonical; local references are rewritten before the LWW merge.

**Code.** `app/lib/sync/entity-mergers.ts#mergeBookRecord`

## Server-wins book merge preserves client-only fields and gates URL clearing on local bytes

**Context.** hasLocalFile and coverImage are never sent to the server, so serverBookToLocal returns them undefined. For remoteCoverUrl/remoteFileUrl, the pull cannot distinguish a row whose URL is null from one where the URL simply was not carried; both map to undefined (server-transforms.ts).

**Decision.** When the remote record wins LWW, keep local hasLocalFile and coverImage. For each remote URL: if the server value is nullish and the device holds the source bytes (book data in the book-data store, or a cover Blob), clear the local URL so uploadPendingFiles re-uploads and re-stamps it, recovering rows that genuinely lost their blob URL. If the server value is nullish and there are no local bytes, keep the locally known URL, since that is usually a pending upload that has not landed and clearing would break the download link.

**Consequences.** Devices holding bytes self-heal lost server URLs at the cost of a re-upload; devices without bytes may keep a URL the server no longer has.

**Code.** `app/lib/sync/entity-mergers.ts#mergeBookRecord`

## Settings merge writes only the synced bucket and filters to SYNCED_SETTINGS_KEYS

**Context.** Settings live in localStorage, split into a synced bucket (app-settings) and a local-only UI bucket (app-ui-settings). Legacy server blobs may still carry UI/layout fields.

**Decision.** mergeSettingsRecord only reads and writes app-settings, never app-ui-settings, and copies only SYNCED_SETTINGS_KEYS from the remote payload. It applies LWW on updatedAt and dispatches settings-changed. Corrupt local JSON is treated as empty and overwritten.

**Consequences.** Legacy server fields can never overwrite or pollute local UI state.

**Code.** `app/lib/sync/entity-mergers.ts#mergeSettingsRecord`

## Upload backoff state is owned by the sync engine and passed through FileUploadContext

**Context.** File upload helpers are called from uploadPendingFiles and reloadBookFiles on different cycles.

**Decision.** The per-book retry Map (keyed bookId:type) lives on the sync engine instance and is passed in FileUploadContext, so a book's backoff survives across both entry points.

**Consequences.** Backoff resets only when the engine is recreated or resetUploadBackoff is called.

**Code.** `app/lib/sync/file-uploads.ts#FileUploadContext`

## One-time backfill of change log for pre-sync data

**Context.** Users who stored books, positions, highlights, bookmarks, notebooks, chat sessions and settings before sync existed have no change-log entries, so push would never upload that data.

**Decision.** runInitialSyncIfNeeded scans every IDB store once and records a put change per existing record (excluding demo content and soft-deleted highlights/bookmarks), then sets the initial-sync-complete flag in the sync flags store. On later runs it only re-queues stranded books (local book data present but no remoteFileUrl and no pending change).

**Consequences.** First sync after the feature shipped pushes all legacy data; the flag prevents repeated full scans.

**Code.** `app/lib/sync/initial-sync.ts#runInitialSyncIfNeeded`

## Only synced settings keys reach the server

**Context.** Legacy localStorage `app-settings` blobs may still contain local-only UI/layout fields that now live in a separate local-only key.

**Decision.** The settings backfill copies only SYNCED_SETTINGS_KEYS from app-settings, and skips recording entirely when none are present (e.g. a blob that only had migrated UI fields). Settings backfill is best-effort and swallows errors.

**Consequences.** Local-only UI state never reaches the server; parse failures do not block initial sync.

**Code.** `app/lib/sync/initial-sync.ts#runInitialSyncIfNeeded`

## Skip malformed IDB entries during sync scans

**Context.** Initial sync and stranded-book scans iterate raw idb-keyval entries, which may include corrupt or partial records.

**Decision.** safeEntry returns null for non-tuple entries, entries with fewer than two slots, or a null/undefined value; callers skip those instead of throwing.

**Consequences.** A single corrupt record cannot abort the whole backfill scan; corrupt records are silently never pushed.

**Code.** `app/lib/sync/initial-sync.ts#safeEntry`

## Chat message merge is append-only with server winning

**Context.** Chat messages are server-authoritative but may exist locally before the server copy arrives.

**Decision.** appendOnlyMerge unions by id and never removes records; on id collision the remote copy replaces the local one so server-side content corrections apply.

**Consequences.** Messages are never lost by merge; local edits to an existing message id are overwritten by the server.

**Code.** `app/lib/sync/merge.ts#appendOnlyMerge`

## Last-write-wins ties favor the server

**Context.** lwwMerge compares updatedAt timestamps between local and remote records; equal timestamps are possible.

**Decision.** When updatedAt is equal, the remote (server) record wins (>= comparison).

**Consequences.** Deterministic convergence across devices; a local edit with an identical timestamp loses to the server copy.

**Code.** `app/lib/sync/merge.ts#lwwMerge`

## Set-union merge prefers tombstones

**Context.** Highlights and bookmarks merge as collections by id across devices; deletes are soft (deletedAt).

**Decision.** setUnionMerge unions by id; if either copy is deleted the tombstone wins; if both are deleted the most recent deletedAt wins; if neither is deleted the later updatedAt wins when both have numeric updatedAt, else local is kept.

**Consequences.** Deletes propagate across devices and cannot be resurrected by a stale non-deleted copy; un-deleting requires a new id.

**Code.** `app/lib/sync/merge.ts#setUnionMerge`

## Per-entity pull cursors

**Context.** Pulling all synced entities with a single cursor forces every entity to re-scan when one lags.

**Decision.** pullChanges sends a `cursors` query param containing a URL-encoded JSON array of SyncCursor ({entityType, cursor}) plus an `entityType` comma list. Entities without a stored cursor are omitted and the server defaults them to epoch (pull from the beginning). Pages are re-requested only for entities whose group reported hasMore.

**Consequences.** One entity's backlog does not cause the others to re-download; the server must accept missing cursors as epoch.

**Code.** `app/lib/sync/pull.ts#pullChanges`, `app/lib/sync/sync-cursors.ts#ParsedPullCursors`, `app/lib/sync/sync-cursors.ts#parseCursorsParam`, `app/lib/sync/types.ts#SyncPullRequest`, `app/routes/api.sync.pull.ts#loader`

## Per-entity sync:entity-updated events

**Context.** Components listen for sync updates; a global event would re-render everything after every pull.

**Decision.** After applying a pulled group with records, dispatch a `sync:entity-updated` CustomEvent with `detail.entity` (wrapped in queueMicrotask) so only components subscribed to that entity react.

**Consequences.** Listeners (useSyncListener) must filter by entity name.

**Code.** `app/lib/sync/pull.ts#pullChanges`

## Pull applies chat_session groups before chat_message groups

**Context.** Chat messages are cached inside their parent session in IDB, so the message merger can only apply a message once its session exists locally.

**Decision.** The server returns chat_session groups before chat_message groups and the pull loop applies groups in that order. When a chat_session group still has more pages, pull.ts defers the chat_message group to a later page.

**Consequences.** Messages are not applied until all paginated parent sessions are merged; a message whose session never arrives is dropped by the merger.

**Code.** `app/lib/sync/pull.ts#pullChanges`

## Rewind only legacy ISO pull cursors

**Context.** Pull cursors were historically ISO timestamps and are rewound slightly to overlap and avoid missing same-timestamp rows; newer servers return opaque JSON keyset cursors.

**Decision.** When persisting a cursor, keep it verbatim if it starts with `{` (opaque keyset cursor, no overlap needed); otherwise apply rewindCursor so legacy ISO cursors keep the duplicate-safe overlap behavior.

**Consequences.** Keyset cursors avoid redundant re-pulls; legacy cursors still re-deliver a small overlap that mergers must tolerate.

**Code.** `app/lib/sync/pull.ts#pullChanges`, `app/lib/sync/types.ts#SyncPullResponse`

## Cap push batches at 50 changes

**Context.** The server processes push entries serially with about 1-3 DB round-trips each, so large batches can exceed Vercel function timeouts.

**Decision.** PUSH_BATCH_SIZE = 50 change-log entries per /api/sync/push request. When a sent batch is full, the engine schedules an immediate follow-up push (scheduleFollowUpPush) instead of waiting for the interval timer.

**Consequences.** Large backlogs drain over several back-to-back requests; each request stays well under the timeout.

**Code.** `app/lib/sync/push.ts#PUSH_BATCH_SIZE`, `app/lib/sync/push.ts#PushContext`, `app/lib/sync/push.ts#pushChangesWithResult`

## Bounded retry for rejected book upserts

**Context.** The server can reject book metadata puts transiently; other rejected entries are terminal. A permanently failing entry must not block the change log.

**Decision.** Rejected book put entries stay unsynced and are retried up to MAX_REJECTED_BOOK_PUSH_ATTEMPTS (3, tracked in memory per change id); accepted entries and terminal rejections are marked synced and cleared each push.

**Consequences.** Transient book rejections recover; persistent ones are dropped after 3 attempts with a warning. Attempt counts reset on page reload.

**Code.** `app/lib/sync/push.ts#pushChangesWithResult`

## Upload book files only after all book upserts are accepted

**Context.** The upload pass scans every local book and the server checks book ownership before accepting a file.

**Decision.** pushChangesWithResult starts uploadPendingFiles only when no pending book put in this push remains unaccepted.

**Consequences.** Uploads do not fail ownership checks for books whose metadata has not reached the server yet; uploads may be delayed by one push cycle.

**Code.** `app/lib/sync/push.ts#pushChangesWithResult`

## Remap local references when server dedups a book

**Context.** The server may map a pushed book to an existing canonical id (same file uploaded from another device).

**Decision.** remapBookId(fromId, toId) moves book data (keeping existing target data), LWW-merges positions and notebooks, rewrites highlights, bookmarks, chat sessions (append-only message merge), the active-session pointer and the chapter-upload cache to toId, then tombstones the losing book record locally. It is a no-op when ids are empty or equal and is safe to run repeatedly.

**Consequences.** All local annotations follow the canonical book; listeners receive a bookIdRemap detail on the book sync event.

**Code.** `app/lib/sync/remap.ts#remapBookId`

## Pulled books have null coverImage until re-download

**Context.** Server BookRow only stores a cover blob URL; local BookMeta.coverImage is a Blob.

**Decision.** serverBookToLocal sets coverImage to null and exposes remoteCoverUrl; the cover Blob is fetched later.

**Consequences.** UI must fall back to remoteCoverUrl for covers of books pulled from another device.

**Code.** `app/lib/sync/server-transforms.ts#serverBookToLocal`

## Chat sessions and messages sync as separate entities

**Context.** Chat sessions locally embed a messages array, but the server stores chat_session and chat_message as separate entity types.

**Decision.** serverChatSessionToLocal returns messages: [] and only maps metadata; chat_message records are merged into sessions by their own merger.

**Consequences.** A pulled session can transiently appear without messages until chat_message pages arrive; pull defers chat_message groups while chat_session has more pages.

**Code.** `app/lib/sync/server-transforms.ts#serverChatSessionToLocal`

## Pull cursors are tracked per entity

**Context.** The original pull protocol used a single since timestamp for all entities. An entity that had fallen behind dragged every other entity's since back with it, causing re-scans and re-delivery of rows other entities had already applied.

**Decision.** The client sends a cursors query param with one cursor per entity type (parsed server-side by parseCursorsParam), and the server queries each entity from its own cursor. Missing entities default to epoch.

**Consequences.** Each entity's pull is isolated; one lagging entity no longer re-delivers rows for the others.

**Code.** `app/lib/sync/sync-cursors.ts#parseCursorsParam`

## Keyset pull cursors keep exact database timestamps

**Context.** Postgres timestamps carry microseconds; JS Date truncates to milliseconds, so a Date-based keyset cursor can skip or repeat rows.

**Decision.** Encoded pull cursors are JSON {t, id} where t is the exact database timestamp string (including fractional microseconds) and id breaks ties; ParsedPullCursors exposes cursorTimestampsByEntity and cursorIdsByEntity alongside the Date map.

**Consequences.** Keyset pagination is exact and needs no overlap rewind; the server must compare using the string timestamp and id.

**Code.** `app/lib/sync/sync-cursors.ts#ParsedPullCursors`

## Rewind ISO pull cursors by 1 ms and rely on idempotent mergers

**Context.** The server pull query filters rows with updatedAt > since. When two rows share the same millisecond and a page ends between them, storing the last row's updatedAt as the cursor would skip the sibling row forever.

**Decision.** For legacy ISO timestamp cursors, the client stores rewindCursor(cursor) = cursor - 1 ms, so the next pull re-delivers rows on the boundary millisecond. Every entity merger must be idempotent so a row delivered twice yields the same stored record as a single delivery. Opaque JSON keyset cursors are stored as-is.

**Consequences.** Boundary rows are re-delivered once per pull; mergers must never accumulate side effects on re-delivery.

**Code.** `app/lib/sync/sync-cursors.ts#rewindCursor`

## Rewind ISO pull cursors by 1ms

**Context.** The legacy pull query uses `updated_at > since`. Advancing the cursor to exactly the last row's updatedAt skips sibling rows that share the same millisecond.

**Decision.** rewindCursor subtracts 1ms from an ISO cursor before storing it, so the next pull overlaps by one millisecond. Unparseable cursors are returned unchanged. This relies on every per-entity merger being idempotent.

**Consequences.** Some rows are re-delivered and re-merged; mergers must treat re-delivery as a no-op.

**Code.** `app/lib/sync/sync-cursors.ts#rewindCursor`

## Opt-in sync debug logging via localStorage

**Context.** Verbose sync diagnostics are useful in the field but noisy, and logs must not leak user content.

**Decision.** syncDebugLog only logs when localStorage `sync_debug` is "1" (enable in a running tab with localStorage.setItem("sync_debug", "1")). Warnings and errors are always logged regardless. The flag gates extra structured diagnostics (upload attempts, push/pull cycle summaries, backoff skips), and only metadata (ids, types, sizes) is logged, never file contents or other PII.

**Consequences.** Debugging a user's sync requires them to set the flag; callers of syncDebugLog must pass metadata only.

**Code.** `app/lib/sync/sync-debug.ts#syncDebugLog`

## In-memory per-book upload retry backoff

**Context.** A book's upload can fail repeatedly (e.g. Vercel Blob 503), and the sync loop runs every 30 seconds.

**Decision.** makeSyncEngine keeps a per-book UploadRetryEntry map, shared with file-uploads through FileUploadContext, that applies backoff between upload attempts. It is in memory only and resets on reload or new engine instance; manual push resets it.

**Consequences.** Failing uploads do not hammer the blob endpoint; a reload retries immediately.

**Code.** `app/lib/sync/sync-engine.ts#makeSyncEngine`

## Normalize sync errors before surfacing

**Context.** Sync cycles sometimes reject with null, undefined, strings or plain objects, which the UI rendered as "null" or "undefined".

**Decision.** normalizeSyncError converts any caught value into an Error with a non-empty message ("Unknown sync error" fallback, wrapping empty-message Errors with cause, JSON-serializing objects) and logs non-Error values to the console for diagnosis.

**Consequences.** UI always shows a meaningful message; raw causes remain in console logs.

**Code.** `app/lib/sync/sync-engine.ts#normalizeSyncError`

## Manual book reload repairs remote copies

**Context.** A book's server row can lack file/cover blob URLs, or downloads can fail, leaving devices unable to fetch it.

**Decision.** SyncEngine.reloadBookFiles re-downloads the file and cover and overwrites local copies; when the remote URL is missing (or download fails) it uploads the local file/cover to blob storage so the DB row gets populated, then re-extracts and re-uploads chapter text when local book data exists.

**Consequences.** A user-triggered reload doubles as a repair path for incomplete server records.

**Code.** `app/lib/sync/sync-engine.ts#SyncEngine`

## Blob paths are scoped by user id

**Context.** File uploads to Vercel Blob need a stable, per-user pathname.

**Decision.** SyncEngineConfig.userId is required and is used in the blob pathname for book file and cover uploads.

**Consequences.** The sync engine can only be created for an authenticated user.

**Code.** `app/lib/sync/sync-engine.ts#SyncEngineConfig`

## Change log deletes are soft deletes

**Context.** Deletes must propagate across devices via merge.

**Decision.** ChangeEntry.operation 'delete' represents a soft delete (tombstone with deletedAt), not physical removal.

**Consequences.** Server and mergers keep tombstones.

**Code.** `app/lib/sync/types.ts#ChangeEntry`

## Change log entries use ULID ids

**Context.** The local change log must be pushed in mutation order and ids must be unique across devices.

**Decision.** ChangeEntry.id is a ULID, giving both uniqueness and chronological ordering.

**Consequences.** Sorting by id yields push order; ids must be generated with a monotonic ULID factory.

**Code.** `app/lib/sync/types.ts#ChangeEntry`

## Merge strategy per entity type

**Context.** Each synced entity has different conflict semantics: single records, deletable collections, and server-authoritative logs.

**Decision.** book, position, notebook, settings and chat_session metadata merge by last-write-wins on updatedAt (ties to server); highlight and bookmark merge by set union on id with tombstones (deletedAt) winning; chat_message is append-only by message id and never removed. Pull cursors are tracked per entity type so entities pull independently.

**Consequences.** Adding an entity requires choosing one of lww, set_union, append_only and adding a merger in entity-mergers.ts and an entry in ENTITY_MERGE_STRATEGIES.

**Code.** `app/lib/sync/types.ts#ENTITY_MERGE_STRATEGIES`

## Client EntityType mirrors server entity_type

**Context.** Entity type strings are shared between the client change log, the pull/push routes and the readmax.sync_cursor.entity_type column.

**Decision.** The EntityType union in app/lib/sync/types.ts must match the server-side readmax.sync_cursor.entity_type values exactly.

**Consequences.** Adding or renaming an entity requires a matching database change.

**Code.** `app/lib/sync/types.ts#EntityType`

## Push response carries canonicalId for deduped books

**Context.** The same book uploaded on two devices gets two client ids.

**Decision.** SyncPushResponse.accepted entries may include canonicalId when the server deduped the entity against an existing record (e.g. same fileHash); the client remaps local references from the change's entityId to canonicalId.

**Consequences.** Clients must run remapBookId for accepted book entries with a differing canonicalId.

**Code.** `app/lib/sync/types.ts#SyncPushResponse`

## Blob upload error classification

**Context.** Upload failures must be split into auth (re-login), transient (retry) and permanent (give up).

**Decision.** Auth only on an explicit signal: BlobAccessError, BlobClientTokenExpiredError, or 401/403/access denied/unauthorized in the message. Permanent: too large, content type, pathname mismatch, precondition, not found, store not found/suspended, aborted. Transient: service unavailable, rate limited, unknown, network/TypeError failures, and 'failed to retrieve the client token'. Anything else is permanent.

**Consequences.** Unknown errors are not retried; auth prompts only on explicit signals.

**Code.** `app/lib/sync/upload-retry.ts#classifyBlobError`

## Classify Vercel Blob errors by constructor name, name, and message

**Context.** @vercel/blob defines its error classes as `var X = class extends BlobError {}`, so err.constructor.name is X but err.name is "Error". instanceof checks are unreliable across bundles.

**Decision.** classifyBlobError matches on err.constructor.name, err.name, and message fragments (e.g. status codes) to decide auth vs transient vs permanent. Tests build stub errors whose constructor name matches the SDK class names.

**Consequences.** Classification depends on SDK class names; an SDK rename needs a matching update.

**Code.** `app/lib/sync/upload-retry.ts#classifyBlobError`

## Treat Blob client-token handshake failures as transient

**Context.** The Vercel Blob SDK wraps every failed token handshake in the same 'Failed to retrieve the client token' error, including 400s for a book whose metadata has not reached the server yet.

**Decision.** classifyBlobError returns transient for that message so the bounded in-call retry can succeed once the book metadata push lands.

**Consequences.** Genuinely invalid token requests are retried a few times before giving up.

**Code.** `app/lib/sync/upload-retry.ts#classifyBlobError`

## Bounded in-call retries for transient upload errors

**Context.** Transient blob failures often clear within seconds; cross-tick backoff alone is slow.

**Decision.** runUploadWithRetry retries transient errors with delays UPLOAD_INCALL_RETRY_DELAYS_MS = 500ms, 2s, 5s (4 attempts total); auth and permanent errors short-circuit and return null.

**Consequences.** A single sync tick can spend up to ~7.5s retrying one upload.

**Code.** `app/lib/sync/upload-retry.ts#runUploadWithRetry`

## Exponential backoff schedule for failing blob uploads

**Context.** Book file/cover uploads that keep failing should not be retried on every 30s sync tick.

**Decision.** Per-book (key bookId:type) failures follow UPLOAD_BACKOFF_SCHEDULE_MS = 30s, 1m, 5m, 15m, 30m by attempt count; attempts past the last slot stay capped at 30 minutes.

**Consequences.** A persistently failing upload retries at most every 30 minutes until reload or manual push resets state.

**Code.** `app/lib/sync/upload-retry.ts#UPLOAD_BACKOFF_SCHEDULE_MS`

## Sync status lives in an external store

**Context.** isSyncing and pending flags flip on every 30s/60s cycle; putting them in React context under SyncProvider re-rendered the whole workspace tree.

**Decision.** Sync status is a module-level external store (emitSyncStatus/subscribeSyncStatus) read with useSyncExternalStore via useSyncStatus. SyncActionsContext only carries stable actions and isActive (useSyncActions). useSyncState combines both and re-renders on every flip, so callers should prefer the split hooks.

**Consequences.** Only components that call useSyncStatus re-render on status flips; status is a process-wide singleton.

**Code.** `app/lib/sync/use-sync.ts#useSyncStatus`

## Process pushed changes parent-first

**Context.** A position/highlight may reference a book in the same batch.

**Decision.** Sort changes by entity order (book before position, highlight, ...) before applying.

**Consequences.** Avoids FK violations within a single push.

**Code.** `app/routes/api.sync.push.ts#action`

## upsertUser updates last_sync_at after accepted pushes

**Context.** Tracking last sync time per user.

**Decision.** When any change is accepted, call upsertUser(userId), which bumps last_sync_at.

**Consequences.** Function name hides the side effect.

**Code.** `app/routes/api.sync.push.ts#action`

## Book push may carry blob URLs

**Context.** Previously only the onUploadCompleted webhook wrote blob URLs, which can be missed.

**Decision.** Push persists remoteCoverUrl/remoteFileUrl via updateBookBlobUrls, using COALESCE so nullish values never overwrite existing URLs; the webhook remains a fast path.

**Consequences.** Two writers for blob URLs; neither can clobber a set value.

**Code.** `app/routes/api.sync.push.ts#processEntry`

## Cross-device book dedup by file hash

**Context.** The same file added on two devices gets two ids.

**Decision.** On book push, if another non-deleted book for the user has the same file_hash, converge to that canonical id and tombstone the incoming id only if it is not already canonical or tombstoned.

**Consequences.** Idempotent across retries; clients must follow the canonical id.

**Code.** `app/routes/api.sync.push.ts#processEntry`

## Deletes are accepted no-ops for positions, notebooks and settings

**Context.** These entities have no tombstone semantics on the server.

**Decision.** Delete operations for position, notebook and settings are acknowledged as accepted without changing data.

**Consequences.** Clients get a clean ack; server rows persist.

**Code.** `app/routes/api.sync.push.ts#processEntry`

## Sync push rejects chat_message entries

**Context.** Chat messages are server-authoritative and written only by /api/chat; accepting client createdAt let clock-skewed clients corrupt ordering.

**Decision.** /api/sync/push returns accepted:false for any chat_message entry. Clients no longer push them.

**Consequences.** Chat history can only change via the chat endpoint.

**Code.** `app/routes/api.sync.push.ts#processEntry`

## CLI pulls book tombstones when grouping sessions

**Context.** Sessions reference books that may have been deleted; deletions can appear on a later page of the pull.

**Decision.** The CLI pulls books with includeDeleted and waits for the complete pull before filtering, so deleted books are excluded instead of appearing as unknown groups.

**Consequences.** Extra pull cost; tests cover deletions on later pages.

**Code.** `packages/cli/src/main.ts`

## CLI repair upload preserves canonical book metadata

**Context.** Re-uploading a book whose canonical record exists but lacks a file should repair the file only.

**Decision.** When a canonical book exists, only its id and remoteFileUrl are pushed, not local metadata.

**Consequences.** Server-side metadata edits are not overwritten.

**Code.** `packages/cli/src/upload.ts`
